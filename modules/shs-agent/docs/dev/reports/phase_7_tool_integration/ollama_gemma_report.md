# Gemma 실제 Ollama 테스트 보고서

실행일: 2026-10-18 KST. 실행 ID: `20261018T071757Z-b18ae842`.

**두 모델 모두 결제 사고 조사를 완료하지 못했다.** `gemma4:26b`는 E4B보다 더 깊은 작업 위임과 실제 Host 권한 전달을 수행했지만, 잘못된 SQL과 컨텍스트 부족 때문에 정답 보고서를 만들지 못했다. 이번 결과는 모델별 동일 시나리오 **1회** 관찰이며 성공률 추정치가 아니다.

## 시나리오와 조건

전자상거래 결제 워커 v2.7.0 배포 이후 중복 결제가 발생한 상황을 재현했다. 실제 로컬 SQLite에 주문 9건과 결제·환불 이벤트를 넣고, Root → analyst → ledger 구조로 조사하도록 했다. 실패·대기 중 결제, 실패한 환불, 부분 환불, 전액 환불, 세 번 결제된 주문, 전날 주문을 구분해야 한다. 정답은 익명 주문 4건, 잔여 초과 결제액 **53,000원**이다. 모델에는 정답 파일을 제공하지 않았다.

실제 모델이 파일을 읽고 Host에게 회계 정책을 질문하며, ledger가 연락처 도구 요청을 거절당한 뒤 읽기 전용 DB 도구를 요청하는 절차를 수행하도록 했다. Host의 답변·거부·승인 정책만 고정했다. Agent의 도구 선택·위임·전달·SQL·완료 응답은 모두 Ollama에서 생성됐다. 실제 고객 데이터나 환불 시스템에는 연결하지 않았다.

공통 설정은 `temperature=0`, `seed=73`, `think=false`, `num_ctx=16384`, 응답 최대 2,048토큰이다. 컨텍스트 압축을 끄고 Root 32단계, 자식 24단계, 깊이 2, 자식 총 2개로 제한했다. 단계 제한과 20분 watchdog에 도달한 모델은 없다. 세부 조건과 한계는 [통합 보고서](ollama_comparison_architecture_report.md)에 있다.

## gemma4:e4b: 선택 인자와 ID 처리 실패

Root의 파일 읽기, Host 질문·응답, 메모와 계획, analyst 생성은 성공했다. analyst는 ledger 생성에서 `plan_ref: {}`를 사용했다. 이 선택 인자를 생략하거나 실제 `plan_id`, `revision`, `item_id`를 전달해야 하지만 같은 오류를 **7회** 반복했다.

그 뒤 실제 task ID 대신 `"ledger"`로 `subagent_wait/status/result`를 호출해 6회 거부됐다. `parent_ask`에는 `related_request_id: "N/A"`를 넣는 등 잘못된 요청 ID를 사용해 2회 거부됐다. ledger가 생성되지 않았기 때문에 연락처 거절, DB 승인, SQL 계산은 수행되지 않았다.

일반 assistant 문자열로 `plan_create(...)` 비슷한 내용을 출력한 응답도 1회 있었다. SDK는 해당 응답을 `tool_calls=null`인 텍스트로 반환했고, 런타임은 이를 임의로 실행하지 않았다. analyst와 Root는 각각 내용과 도구 호출이 모두 없는 응답으로 끝났으며 최종 `stop_reason`은 `empty_response`다.

**관찰 판정:** 잘못된 ID와 불완전한 계획 참조를 차단한 검증은 작동했다. 하지만 모델이 오류에서 회복하지 못했고, 하위 작업이 성공적으로 생성됐다고 질문 문장에서 주장하기도 했다. 이 주장은 실행 사실이 아니다. trace는 실제 생성된 작업이 2개뿐임을 보여 준다.

주요 증거는 [E4B 재검토 결과](../../../build/ollama_tool_integration/20261018T071757Z-b18ae842/gemma4_e4b/evidence_review.json)의 `failure_counts`, `failures`, `plain_assistant_responses`, `empty_responses`와 [전체 trace](../../../build/ollama_tool_integration/20261018T071757Z-b18ae842/gemma4_e4b/tree.json)다. 첫 잘못된 spawn은 analyst `5e02c2c4bf4842a19e198a38dc76cc10`, sequence 83, 인자 artifact `8574817e38e6496d8d2df2a027c401a1`에 있다.

## gemma4:26b: 권한 전달 성공, 업무 조사 실패

1. Root → analyst → ledger 작업 3개를 실제로 생성했다.
2. ledger의 연락처 요청이 analyst와 Root를 거쳐 Host에 도달했다. Host는 거부했고 연락처 도구는 어느 작업에도 제공되거나 실행되지 않았다.
3. `plan_revise`에 `items` 대신 `updates`를 넣어 실패했다. 이후 `plan_update`는 성공했으나 요구한 계획 구성 변경(`plan_revised`)은 발생하지 않았다.
4. DB 요청은 두 hop을 거쳐 Host에 도달했다. 승인 후 원래 요청자인 ledger의 도구 집합만 revision 1로 바뀌었다. Root와 analyst에는 DB 도구가 나타나지 않았다.
5. ledger는 `schema.md`를 읽지 않고 실제 DB 도구를 호출했다. SQL에서 `events`, `total_amount_krw`, `event_type` 등 실제 스키마와 다른 이름을 사용했다. SQLite는 `no such table: events`를 반환했다. 성공한 조회와 계산 결과는 없다.
6. analyst 응답은 `done_reason=length`로 종료됐고, 자식 ledger가 취소됐다. Root는 자식 결과를 가져온 뒤 대화 검색·읽기를 반복했고 최종적으로 빈 응답으로 실패했다.

DB 요청 ID는 `8e36fe8903ca4f1085a8880b25d11d73`, 적용 대상은 ledger `e53ea89ccb154c7eb733e756f322c363`다. [전체 trace](../../../build/ollama_tool_integration/20261018T071757Z-b18ae842/gemma4_26b/tree.json)의 ledger sequence 191–192에서 도구 집합 변경과 적용을 확인할 수 있다. Root sequence 225/227에는 Host 요청/승인이 있다. [실행 결과](../../../build/ollama_tool_integration/20261018T071757Z-b18ae842/gemma4_26b/result.json)의 `fixture_operations`에 실제 실패 SQL이 보존돼 있다.

### 컨텍스트와 복구 경로

analyst의 잘린 응답은 입력 **16,255**토큰, 출력 **129**토큰이었다. 합계가 `num_ctx=16384`와 같다. 응답별 `max_tokens=2048`을 모두 사용한 상황이 아니다. 원본 서버 로그에도 `truncated=1`이 있다. 이 실패는 고정 컨텍스트와 압축 비활성화 조건의 영향을 받았으므로 모델 크기나 추론 능력만으로 설명하면 안 된다.

Root는 `conversation_search` 7회, `conversation_read` 6회를 호출했다. 검색 결과를 다시 검색하고, 읽은 결과를 다시 읽으면서 JSON 이스케이프가 중첩됐다. 가장 큰 Root 요청의 메시지 JSON 길이는 **115,474자**였으며 단일 tool 메시지는 JSON 기준 **13,562자**까지 커졌다. 이는 모델의 잘못된 복구 행동에 더해, 이전 검색 결과까지 다시 검색할 수 있는 현재 검색 정책이 문맥 팽창을 허용함을 보여 준다. 원본 데이터 보존과 LLM에 다시 넣는 검색 결과의 선택·표현을 구분하는 개선이 필요하다.

Host는 DB 실행 시 익명 ID와 수동 검토 지시를 Root에 추가했다. 런타임은 진행 중이던 오래된 응답을 `new_host_instruction`으로 폐기한 뒤 지시를 적용했다. 이 동작은 관찰됐지만 최종 보고서가 없으므로 최종 답변이 지시를 준수하는지는 검증하지 못했다.

`host_cancelled`라는 ledger 종료 사유는 이 실행에서는 사람이 취소했다는 뜻이 아니다. analyst 종료에 따른 자식 정리 경로가 취소를 요청했다. 부모 종료와 사용자 취소를 구분하는 사유 기록은 관측성 개선 후보다.

## 크기 차이와 적용 판단

26B는 실제 도구 전달·승인·격리 경로까지 진행했고, 도구 오류 비율도 E4B보다 낮았다. 이 한 번의 시나리오에서는 더 긴 절차를 처리한 증거가 있다. 그러나 두 모델 모두 정답을 내지 못했으므로 26B가 운영 준비를 마쳤다고 판단할 수 없다.

E4B의 생성 속도는 약 **1.69배** 높았다. 26B의 전체 실행 시간은 약 **5.11배**였지만 호출 수, 작업 깊이, 입력 재처리량이 다르므로 이 값을 동일 작업의 순수 속도비로 쓰면 안 된다. 26B는 `/api/ps`상 할당 크기의 약 72.7%가 VRAM에 있었다. 서버는 동시에 `offloaded 31/31 layers to GPU`, CUDA 모델 버퍼 11,868.46 MiB, CUDA_Host 모델 버퍼 4,710.53 MiB를 기록했다. **VRAM 비율을 GPU 연산 비율 또는 CPU 레이어 수로 바꾸어 해석할 수 없다.** 메모리 배치·expert 구조·긴 문맥을 함께 고려해야 한다. 근거는 [서버 관측 기록](../../../build/ollama_tool_integration/20261018T071757Z-b18ae842/server_observations.json)이다.

우선 개선할 항목은 선택 인자 생략 안내와 구조화된 인자 오류, 정확한 request/task ID 안내, 스키마 읽기 후 SQL 작성, 검색 결과 재검색 억제, 응답 공간을 남기는 컨텍스트 예산 관리다. **ID 검증을 느슨하게 하거나 자연어 승인으로 도구를 열어 주는 방식은 개선안에 포함하지 않는다.**

## 검증 범위

두 실행 모두 live 이벤트와 최종 trace 일치, state cursor 재생, tree JSON 왕복, 도구 호출 출처, 관측/Host 처리 오류 없음이 확인됐다. SDK 응답 내용·도구 인자와 공통 응답 사이의 손실은 79개 응답에서 발견되지 않았다. 이는 SDK 경계 이후의 비교이며 HTTP 원시 바이트 전체 검증은 아니다.

권한 전달·격리·적용 시점은 26B에서 확인됐다. E4B에서는 해당 경로에 도달하지 않아 미검증이다. 성공적인 SQL 결과 전달, 3개 작업의 완료, 정답 보고서, 압축 활성화 상태의 동작은 두 실행으로 확인하지 못했다. 원시 자동 판정의 미실행 항목은 [재검토 스크립트](../../../tests/review_ollama_tool_integration.py)에서 `not_observed`로 구분했으며 원본 결과 파일은 수정하지 않았다.

전체 조건·원본 로그 목록·아키텍처 개선 우선순위는 [통합 보고서](ollama_comparison_architecture_report.md), Qwen 결과는 [Qwen 보고서](ollama_qwen_report.md)를 참조한다.
