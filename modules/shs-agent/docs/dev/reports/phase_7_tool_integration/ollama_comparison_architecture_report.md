## 실제 수행한 작업

결제 워커 배포 후 재시도와 멱등성 문제가 의심되는 사고를 조사하게 했다. 데이터는 이번 테스트를 위해 만든 로컬 합성 복제본이며, 파일 읽기와 SQL은 실제 실행했다. 모델이 문장을 그럴듯하게 생성하는 것만으로는 성공할 수 없도록 실제 주문 ID·이벤트 ID·DB 출처와 계산값을 확인했다.

정답은 4건, **53,000원**이다. 날짜 기준은 `orders.created_at`의 2026-10-17 UTC이고, `succeeded` capture만 더하고 `succeeded` refund만 빼야 한다. 실제 ID는 `ORD-7f1d4e0ab6-101` 형식이다. [oracle](../../../build/ollama_tool_integration/20261018T071757Z-b18ae842/fixture/oracle.json)은 Host 평가에만 사용했고 모델에는 노출하지 않았다.

검증 절차는 다음과 같다.

1. Root가 사고 파일을 읽고 Host에 회계·환불 정책을 질문한다. Host는 실제 `question_id`에 답한다.
2. Root가 analyst를, analyst가 ledger를 생성한다. 각 작업은 계획·문맥·도구 집합을 따로 가진다.
3. ledger가 연락처 도구를 요청한다. analyst와 Root가 실제 요청을 전달해야 Host가 거부한다.
4. ledger가 익명 분석으로 계획을 바꾸고 DB 도구를 요청한다. Host는 원래 요청자의 정확한 request ID에 승인한다.
5. 적용된 ledger만 SQLite를 조회한다. DB 실행 시 Host가 Root에 익명 ID와 수동 검토 지시를 추가한다.
6. 증거를 ledger → analyst → Root로 전달하고 Root가 구조화된 최종 보고서로 완료한다.

권한 거부와 회복을 반드시 관찰하도록 절차를 명시한 통합 시나리오다. 완전히 자유로운 업무 평가나 여러 종류의 업무를 포괄하는 벤치마크는 아니다. DB·파일은 실제 도구이고, 대답·도구 호출·자식 생성·전달을 테스트 코드가 대신 만들어 주지 않았다. 연락처 도구는 권한 통제를 검사하기 위한 카탈로그 항목이다.

## 아키텍처에서 확인한 동작

실행된 경로와 미실행 경로를 구분한다. 워크플로 실패는 업무 수용 기준 실패이며, 그 자체가 모든 런타임 기능의 오류를 뜻하지 않는다.

| 항목 | 관찰 근거와 해석 |
|---|---|
| Task별 도구 격리 | Gemma 26B의 DB 도구는 승인 대상 ledger에만 노출됐다. Root와 analyst는 권한을 상속하지 않았다. |
| 요청·전달·Host 결정 분리 | Gemma 26B의 연락처 거부와 DB 승인이 원래 요청 ID 및 두 hop으로 연결됐다. 자연어 `agent_reply`는 권한을 부여하지 않았다. |
| 승인과 적용 분리 | 승인 후 ledger의 도구 revision 1과 `tool_access_applied`가 기록되고, 그 다음 LLM 요청부터 DB 스키마가 제공됐다. 실행 중인 도구가 남은 상태에서 도구 집합을 교체한 기록은 없었다. |
| 잘못된 ID 차단 | E4B의 `ledger`·`N/A`, Gemma 26B의 잘못된 수신자에 대한 응답이 거부됐다. |
| Host 추가 지시 | Gemma 26B에서 진행 중인 Root 응답이 `new_host_instruction`으로 폐기되고 명령이 적용됐다. 최종 답변 준수는 별도 검증이 필요하다. |
| 부분 응답·빈 응답 처리 | `length` 응답을 정상 완료로 인정하지 않고 중단했다. 빈 응답도 `empty_response`로 명시해 실패했다. |

이 실험으로 임의의 권한 조합, 악의적 요청, 재시작 복구, 네트워크 장애, 높은 동시 부하, 승인 취소, 모든 레이스를 검증한 것은 아니다. 실제 모델이 도달하지 않은 기능을 성공으로 처리하지 않는다.

## 발견한 문제와 개선 우선순위

### 1. 컨텍스트 예산과 검색 결과 중첩 — 우선순위 높음

Gemma 26B analyst는 입력 16,255 + 출력 129토큰에서 `length`로 종료했다. Root는 검색·읽기 결과를 다시 검색·읽어 메시지 JSON이 115,474자까지 증가했다. [conversation.search](../../../src/shs_agent/agent/context/conversation.py)는 현재 호출을 제외한 모든 메시지를 검색하므로 이전 검색 결과도 후보에 들어간다. read 결과의 JSON 재직렬화는 이스케이프를 누적할 수 있다.

개선안은 검색 결과 메시지를 기본 후보에서 제외하거나 원본 참조로 정규화하고, 반복 조회를 감지하며, 모델 컨텍스트에서 출력 공간을 먼저 확보하는 것이다. 기본 압축은 48,000자 임계값이지만 이번 테스트에서는 껐다. 따라서 **기본 압축 자체가 고장 났다는 증거는 없다.** 압축을 켠 운영 설정과 모델별 토큰 예산으로 별도 검증해야 한다. 컨텍스트를 무조건 늘리면 16GB GPU에서 offload와 지연이 늘 수 있다.

### 2. 인자 오류를 고치기 어려운 도구 인터페이스 — 우선순위 높음

E4B는 선택 `plan_ref`를 `{}`로 채웠고 존재하지 않는 ID를 반복했다. Gemma 26B는 `plan_revise`에 `updates`를 넣었다. 스키마는 정확한 필드를 선언하지만 [ToolExecutor](../../../src/shs_agent/tool/executor.py)는 일반 JSON Schema 검증 없이 handler에 kwargs를 전달한다. 이 때문에 일부 오류는 Python `TypeError`로 반환된다. 도구 제공 여부·revision 검증과 인자 전체 검증은 다른 층이다.

실행 전 인자 검증과 `expected_fields`, 누락/불필요 필드, 선택 인자 생략 방법, 올바른 짧은 예제를 제공하면 회복에 도움이 된다. 현재 요청·수신자·계획 참조 검증은 유지해야 한다. 임의 ID를 실제 ID로 추정해 바꾸는 보정은 하지 않는다.

### 3. 도구 전달과 일반 대화의 혼동 — 우선순위 중간

Gemma 26B는 전달 후 `agent_reply`를 불필요하게 호출했고, 원래 요청 ID와 전달된 hop ID 또는 수신자를 혼동했다. 전용 `tool_wait` 대신 `agent_wait_reply`를 사용하기도 했다. 실제 권한은 Host API만 부여했으므로 무단 실행으로 이어지지는 않았다.

LLM에 제공하는 요청 상태에 `original_request_id`, 현재 hop, 응답 권한, 다음 허용 동작을 더 명확히 요약하고, 완료된 권한 결정을 다시 응답하려는 경우의 안내를 개선할 수 있다. 권한 도구와 일반 대화 도구가 많은 스키마에 함께 제시되는 부담도 평가 대상이다.

### 4. 데이터 스키마 확인과 업무 수용 기준 — 우선순위 높음

Gemma 26B는 스키마 파일을 건너뛰고 존재하지 않는 테이블·열을 조회했다. 읽기 전용 SQLite는 오류를 정상 반환했지만 그 뒤 실제 분석 결과는 나오지 않았다. 도구가 실행됐다는 사실과 SQL이 성공했다는 사실, 정답이 나왔다는 사실을 각각 구분해야 한다.

운영용 Host는 `TaskStatus.COMPLETED`와 별도로 필수 필드, 실제 증거 ID, 합계·행 수·정책 준수를 평가해야 한다. 이 테스트는 정답 oracle로 평가했으나 일반 운영에서는 검증 SQL과 데이터 출처 검사가 필요하다. 사용자에게 영향을 주는 조치는 검토 제안과 실제 실행을 별도로 다뤄야 한다.

### 5. 빈 응답·취소 원인 관측성 — 우선순위 중간

Qwen 9B는 첫 SDK 응답부터 내용과 도구 호출이 없었다. 공통 응답 변환 과정에서 사라진 것은 아니다. 모델 템플릿·서버 디코더·생성 옵션 중 무엇이 원인인지 한 번의 실행으로는 확정할 수 없다. 빈 응답 실패를 그대로 보존한 것은 적절하다. 복구가 필요하다면 Host가 허용한 제한적 재시도나 모델 전환을 별도 정책으로 설계하고 재시도 횟수를 보고해야 한다.

부모 종료가 유발한 자식 취소도 `host_cancelled`로 기록되므로, `parent_finished`와 사용자 취소를 구분하는 원인 정보가 있으면 장애 분석이 쉬워진다.

### 6. 복구 정책과 Host 스텁 — 우선순위 높음

Qwen 27B는 ledger가 빈 응답으로 실패한 뒤 새 자식을 요청했지만 총 생성 예산 2개를 이미 소진했다. 이후 Root가 복구 방안을 질문해도 고정 Host는 회계 정책만 반복했다. 최초 질문 1회 이후 복구 질문 9회가 이어졌고, Root 문맥이 16K 경계에 도달해 `length`로 끝났다.

이는 이번 하네스가 실제 사람의 복구 판단을 대체하지 못한 한계다. Qwen 27B의 최초 ledger 실패는 280.71초, 전체 종료는 542.53초였으므로 후반 시간을 순수 모델 성능으로 해석하면 안 된다. 운영 Host에는 질문 종류별 응답, 명시적 복구 거절 또는 허용 정책, 반복 질문 제어가 필요하다. 승인 목록 밖인 analyst에 임의로 DB를 부여하거나 실행 중 실험 조건을 바꾸지는 않았다.

## 결과 해석의 한계

- 각 모델 1회이므로 안정적인 성공률·평균 지연·통계적 우열을 주장할 수 없다. seed 고정도 GPU·서버 스케줄링의 완전한 재현을 보장하지 않는다.
- 파라미터 수뿐 아니라 계열, 템플릿, expert 구조, 저장 옵션, 부분 CPU 실행, 문맥 길이, 실제 호출 수가 다르다. 같은 양자화 표기만으로 이를 통제했다고 볼 수 없다.
- `think=false`, 16K 컨텍스트, 압축 비활성화는 이번 조건이다. 모델 권장 설정 전반이나 기본 shs-agent 설정의 성능으로 일반화하지 않는다.
- cold load를 포함한 경과 시간과 provider 생성 속도를 나눠 보고했다. 실패가 빨리 끝났다고 유용한 작업 처리량이 높은 것은 아니다.
- LLM 지연 합계는 Root와 자식의 대기·중첩 호출을 포함한다. 전체 경과 시간과 같지 않으며 SDK 호출 중첩은 병렬 GPU 추론의 증거가 아니다.
- 15초 자원 표본은 짧은 실행과 순간 최고치를 놓칠 수 있다. GPU 전체 사용량은 모델 VRAM과 다르다.

## 증거와 재현

실행 원본은 [run 폴더](../../../build/ollama_tool_integration/20261018T071757Z-b18ae842)에 있다. 모델별 `setup.json`, `live.jsonl`, `tree.json`, `result.json`, `resources.json`, `summary.json`, `unload.json`을 보존한다. `executed_verify_ollama_tool_integration.py`는 실행 당시 스크립트 사본이다.

[서버 로그 발췌](../../../build/ollama_tool_integration/20261018T071757Z-b18ae842/ollama_server_excerpt.log)와 [줄 번호·주요 관측](../../../build/ollama_tool_integration/20261018T071757Z-b18ae842/server_observations.json)에는 실제 GPU 배치와 컨텍스트 잘림을 보존했다. Gemma 26B는 `31/31 layers` GPU 배치와 별도의 CUDA_Host 버퍼를 함께 보고하므로 `/api/ps` VRAM 비율만으로 CPU 레이어 수를 추정하지 않았다. Qwen 27B는 `46/66 layers` GPU 배치를 보고했다.

- [실행 스크립트](../../../tests/verify_ollama_tool_integration.py): `python tests/verify_ollama_tool_integration.py`. 다시 실행하면 새 모델 실험이므로 이번 1회 결과와 섞으면 안 된다.
- [오프라인 재검토](../../../tests/review_ollama_tool_integration.py): `python tests/review_ollama_tool_integration.py build/ollama_tool_integration/20261018T071757Z-b18ae842`. 모델 호출 없이 저장된 증거만 읽는다.
- [재검토 집계](../../../build/ollama_tool_integration/20261018T071757Z-b18ae842/evidence_review.json): 보고서 수치와 미검증 구분의 근거다.

실행 스크립트의 종료 코드 0은 전체 실험 기록 수집이 끝났다는 뜻이다. 업무 성공 여부는 각 모델의 `business_success`와 세부 수용 기준으로 확인해야 한다.

원시 자동 판정에는 미실행 경로에서 `all([])` 또는 초기 `True`가 통과로 표시될 수 있는 한계가 있었다. 원본 `summary.json`은 그대로 보존하고, 별도 `evidence_review.json`에서 선행 사건이 없는 항목을 `not_observed`로 바꿨다. 업무 결과의 실패 판정은 유지했다. 또한 빈 응답 1토큰·1마이크로초로 계산된 비현실적인 생성 속도는 성능 비교에서 제외했다. 재검토 파일에는 원본 SHA-256이 들어 있다.

실행 전후 모든 `src/**/*.py` SHA-256이 일치했다(`source_unchanged=true`). 이번 작업에서는 제품 엔진을 바꾸지 않고 실행·재검토 스크립트와 보고서를 추가했다. 기존 회귀 테스트 **228개가 27.742초에 모두 통과**했으며 [로그](../../../build/ollama_tool_integration/20261018T071757Z-b18ae842/regression_tests.log)를 보존했다.

네 실행 모두 tree/details 종료, live 이벤트 일치, state cursor 재생, JSON 왕복, 관측 및 Host 처리 예외 없음이 확인됐다. SDK 응답 118개에서 공통 응답으로의 내용·도구 인자 손실은 없었다. 이것은 SDK 경계의 무결성과 엔진 회귀 검증이며, **실제 모델의 업무 완수 검증을 대신하지 않는다.**
