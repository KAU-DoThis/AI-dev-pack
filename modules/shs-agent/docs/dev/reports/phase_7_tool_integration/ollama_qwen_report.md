## 결론과 실측

## 실제 업무와 설정

배포 후 중복 결제가 발생한 전자상거래 사고를 조사하도록 했다. 실제 로컬 SQLite의 주문 9건과 결제·환불 이벤트에서 실패·대기, 부분·전액 환불, 세 번 중복 결제, 전날 주문을 구분해야 한다. 정답은 익명 주문 4건, 초과 결제 **53,000원**이다. 실제 고객 시스템이 아닌 합성 복제본을 사용했으며, 모델에는 oracle을 제공하지 않았다.

Root → analyst → ledger 위임, 연락처 도구 요청·Host 거절, 계획 변경, DB 도구 요청·승인·적용, SQL 실행과 상향 결과 전달을 동일하게 지시했다. Host는 고정된 회계 정책에 답하고 정해진 권한 결정만 수행했다. Agent의 모든 행동은 실제 Ollama 응답으로 결정됐다.

각 모델은 전체 워크플로 **1회** 실행했다. 동일한 `temperature=0`, `seed=73`, `think=false`, 16,384 컨텍스트, 최대 출력 2,048토큰을 사용했고, 압축은 껐다. Root 32단계, 자식 24단계, 총 자식 2개·깊이 2로 제한했다. 실패한 모델을 다시 실행하거나 응답을 고쳐 넣지 않았다. 전체 조건과 정답 데이터는 [통합 보고서](ollama_comparison_architecture_report.md)에 있다.

## qwen3.5:9b: 첫 SDK 응답이 비어 있음

첫 LLM 호출은 약 7.51초, 전체 워크플로는 **7.54초**였다. 그중 모델 로드는 **6.71초**였다. SDK는 다음과 같은 응답을 반환했다.

```json
{
  "done": true,
  "done_reason": "stop",
  "prompt_eval_count": 4165,
  "eval_count": 1,
  "eval_duration": 1000,
  "message": {"role": "assistant", "content": "", "thinking": null, "tool_calls": null}
}
```

공통 응답과 정규화 응답도 비어 있었다. 도구 0회, 자식 0개이며 `failed / empty_response`로 종료했다. 이는 도구 실행·권한 거부·SQL 오류에 도달하기 전의 실패다. SDK 경계에서 이미 빈 값이므로 shs-agent의 공통 응답 변환이 내용을 잃었다는 증거는 없다. 모델·템플릿·서버 디코더·`think=false` 중 어느 요소가 원인인지는 이 1회 실행만으로 확정할 수 없다.

1토큰과 1마이크로초를 나누면 원시 집계가 1,000,000 token/s가 되지만 유용한 생성 속도가 아니다. 보고서에서는 **N/A**로 표시한다. 7.54초의 빠른 종료도 업무 처리 속도가 빠르다는 뜻이 아니다. 15초 자원 표본보다 실행이 짧아 로드 후 `/api/ps` 표본은 얻지 못했다.

[Qwen 9B trace](../../../build/ollama_tool_integration/20261018T071757Z-b18ae842/qwen3_5_9b/tree.json), [재검토 결과](../../../build/ollama_tool_integration/20261018T071757Z-b18ae842/qwen3_5_9b/evidence_review.json)에 응답과 종료 근거가 있다.

## qwen3.8:27b: 요청자 종료와 복구 실패

Qwen 27B는 Root·analyst·ledger 3개 작업을 만들었다. Root와 자식들이 사고 파일·스키마를 읽었고 Host 회계 정책도 전달했다. `plan_update`에 잘못된 `items` 인자를 넣은 오류가 Root와 analyst에서 각각 발생했지만, 이후 `updates`를 사용해 회복했다.

ledger는 연락처 도구를 요청한 직후 다음 LLM 응답이 비어 있어 **Root 생성 약 280.71초 후** 실패했다. 원래 요청 ID는 `6821c00a0e1147359bcc853ca09b0615`, ledger task ID는 `324411fe059b4e4796ce74655272e303`다. 이 시점에는 Host까지 요청이 전달되지 않았다. 따라서 이 실행에서 **Host가 연락처 요청을 거부한 사실은 없다.**

analyst가 뒤늦게 요청을 전달했을 때는 요청자가 이미 종료돼 있었다. `tool_forward`는 `only the current direct recipient may forward a pending request`로 거부됐다. 이 문장만 보면 수신자 오류처럼 보이지만 trace의 시간 순서는 요청 종료가 먼저다. 요청이 닫힌 경우와 수신자가 틀린 경우를 구분하는 오류 메시지가 있으면 원인 파악에 도움이 된다.

analyst는 실패한 ledger 결과를 가져온 뒤 새 ledger를 만들려 했으나 `max_total_subagents reached`로 거부됐다. 예산은 현재 실행 중인 개수가 아닌 전체 생성 수 기준으로 소진돼 있었다. 이는 테스트의 고정 제한이며, 재시도까지 허용한 운영 정책의 복구 능력을 측정한 결과는 아니다. analyst도 이후 빈 응답으로 종료됐다.

Root는 늦게 `agent_reply`를 보냈고, 도구 handler 호출 자체는 성공했지만 반환값은 다음과 같았다.

```json
{"accepted": false, "reason": "request_closed", "request_status": "requester_terminated"}
```

이는 종료된 요청을 되살리거나 메시지를 전달한 성공이 아니다. 도구 실행 상태 `succeeded`만으로 비즈니스 동작의 수락 여부를 판정하면 안 되는 사례다. Root와 analyst가 실패한 자식의 결과를 가져오는 경로는 작동했다.

### Root의 원인 설명 오류와 Host 스텁 한계

Root는 복구 질문에서 “연락처가 거절된 뒤 ledger가 자식 수 제한에 걸렸다”는 취지로 설명했다. 실제 순서는 **ledger의 빈 응답 → 요청 종료 → analyst의 전달 실패 → 대체 자식 생성 제한**이다. 모델의 원인 설명은 trace와 일치하지 않았다.

그 뒤 Root는 자식 예산 초기화, analyst에 DB 직접 승인, 새 analyst 생성 중 어떤 조치를 취할지 Host에 물었다. 하지만 테스트 Host는 모든 질문에 같은 회계 정책만 답하도록 만들어져 있어 운영 복구 질문에 답하지 못했다. 반복 질의 시간은 **모델과 고정 Host 응답 정책의 상호작용**이며 모델의 순수 추론 지연으로 해석해서는 안 된다. 한 번의 실험 중 Host 정책을 바꾸지 않고 원본 그대로 보존했다.

실제 운영에서는 질문 종류에 맞는 답변, 불가능한 복구 조치의 명확한 거절, 권한 내 대안, 동일 질문 반복 차단이 필요하다. 테스트의 첫 ledger 실패는 이 반복 질의 전에 발생했으므로 Host 스텁이 최초 빈 응답을 일으켰다는 뜻은 아니다.

Host 질문은 최초 회계 질문 1회와 복구 질문 9회, 총 **10회**였다. Root는 22번째 판단에서 `done_reason=length`로 끝났다. 이때 입력 16,139토큰, 생성 242토큰이 보고됐고 서버는 `truncated=1`, `n_tokens=16383`을 기록했다. 2,048 출력 토큰을 모두 사용한 것이 아니라 16K 컨텍스트 경계에 닿은 상황이다. Root 32단계 제한이나 20분 watchdog은 도달하지 않았다. 최종 출력은 빈 문자열이며 어떤 작업에서도 계산 결과가 나오지 않았다.

## 모델 크기와 아키텍처 판단

9B는 첫 응답에서 실패했고, 27B는 위임·파일 읽기·계획 오류 수정·실패한 자식 결과 회수까지 진행했다. 이 실행에서 27B가 더 많은 절차를 수행한 것은 확인되지만, 업무 정답을 얻지 못했으므로 크기 증가가 실무 성공을 보장한다고 결론내릴 수 없다.

로컬 메타데이터는 각각 전체 **9.7B / 27.3B**, Q4_K_M로 보고했다. `qwen3.8:27b`의 family는 `qwen35`, parent는 `qwen3.8:27b-q4_K_M`이다. 요청한 로컬 태그를 그대로 사용했으며 공식 배포 계보를 별도로 추정하지 않았다. 두 모델의 GPU 레이어 배치가 다르므로 단순 크기 대 속도비를 계산하지 않는다.

서버 로그상 GPU offload는 9B **34/34 레이어**, 27B **46/66 레이어**였다. 27B의 `/api/ps` VRAM 비율은 약 67.2%였으나 이를 GPU 연산 비율로 보지는 않는다. 이 메모리 조건과 후반 Host 반복 질의가 전체 지연 비교를 제한한다. 로그 발췌와 원래 줄 번호는 [서버 관측 기록](../../../build/ollama_tool_integration/20261018T071757Z-b18ae842/server_observations.json)에 있다.

빈 응답 감지, 종료된 요청의 전달 방지, 총 자식 예산, 종료 후 회신의 미수락, 실패 결과 회수는 실제 경로에서 확인했다. 그러나 Qwen 두 실행 모두 DB 승인·적용·실행에 도달하지 못했다. **Qwen으로 7단계의 전체 성공 경로를 검증했다는 주장은 할 수 없다.**

첫 빈 응답 원인을 조사하는 별도 최소 프롬프트·템플릿 실험, 생각 모드와 컨텍스트 설정 비교, 운영 Host의 복구 정책이 다음 검증 항목이다. 이번 요청의 모델별 1회 조건을 유지하기 위해 추가 추론 실험은 하지 않았다.

두 Qwen 실행의 39개 SDK 응답에서 공통 응답으로의 내용·도구 인자 손실은 발견되지 않았다. live 이벤트와 최종 trace 일치, state cursor 재생, tree JSON 왕복, 관측/Host 처리 예외 없음도 통과했다. Host 처리에 예외가 없었다는 것과 Host 답변이 복구 질문에 적절했다는 것은 다른 평가다.
